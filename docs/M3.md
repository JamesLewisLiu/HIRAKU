# M3: attract mode and BGA, checked against MAME (2026-10-11)

Two different questions, answered separately, so that timing differences between the two machines cannot hide or fake a result.

## 1. Is the renderer exact? Bit-exact on 28/28 frames

- **Method:** MAME runs `bm3final-practice.his` with its GCU accesses recorded unfolded (`HIRAKU_TAPS=gcu HIRAKU_NOFOLD=gcu oracle/mame.sh ...`; 14.8M records). `gcu_replay` (`tests/gcu/`) feeds all 14.5M GCU writes into HIRAKU's K057714 and renders the frames MAME took snapshots of.
- **Result:** **every one of the 28 snapshots (frames 3600–11700) is pixel-identical** to MAME's own screenshot. They cover attract, menus, the tutorial pages, notes, BGA layers and judgement graphics.
- **Alignment:** MAME's snapshot at frame N equals the state after every write labelled before N (consistently).

```bash
HIRAKU_TAPS=gcu HIRAKU_NOFOLD=gcu oracle/mame.sh bm3final oracle/scripts/bm3final-practice.his gcu-replay
build/cmake/tests/gcu_replay out/oracle/bm3final/gcu-replay/mmio.bin out/gcu-replay $(seq 3600 300 11700)
```

## 2. Is the game logic exact? The BGA engine in lockstep with MAME

- **Method:** `oracle/scripts/bm3final-bga.his` is the practice run without key presses during the song, so every note is a deterministic miss. It hashes every frame:
  - the BGA object pool (`0x80146750`, 16 KiB);
  - the VM state (`0x80255de0`–`0x80256700`);
  - plus the bar counter and the scene id.

  MAME and HIRAKU run it unchanged.
- **Result:**
  - The song starts **13 frames later** in HIRAKU (constant over all 56 bars; loading time).
  - At that offset, the object pool and VM state are **byte-identical on 7,470 of 7,563 song frames (98.8%)**.
  - The rest: 70 frames in the first two seconds of the song (scene setup), and seven isolated spots, six of them single frames (events landing a frame apart).
- **Why the practice script itself scores lower (41%):** it presses keys at fixed frame numbers. With the song 13 frames late, the presses hit different notes and the BGA's hit/miss reactions differ, as they should.

### Update (after M5's timing change)

Native code is now charged one virtual tick per executed instruction, as in MAME, instead of per poll. Two effects:
- **The song now starts 1–2 frames from MAME's, instead of 13.**
- **Per-frame object-pool equality depends on where the song falls inside a frame.** Objects are created on one frame or the next, which shifts their animation counters for their whole life. So:
  - *frame-indexed* object-pool equality dropped to about 6%;
  - the **sequence of BGA VM states still matches MAME's in order at 97.7%** (5,318 of 5,444 distinct states).
- **The earlier 98.8% figure** was measured under the old cost model and partly reflected a favourable in-frame alignment.

A phase-independent object comparison (aligning object lifetimes rather than frames) is still to do.

## 3. Coverage

A full practice session (`bm3final-practice.his`, 12,000 frames) produces **no interpreter fallbacks, no unmapped device accesses and no unsupported device commands**.

## What is not claimed

- **Identical screenshots at the same frame number:** HIRAKU's clock is not MAME's, so animations differ in phase. Section 2 compares the logic; section 1 compares the pixels.
- **The 13-frame song-start offset:** not investigated. Disc and HDD loading are faster in HIRAKU (instant ATA/ATAPI), and that is the likely cause.
