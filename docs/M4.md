# M4: the SPU sound board (2026-10-11)

## What runs

beatmania III The Final, natively, with its sound board:
- **Self-test:** every check passes (I/O, IBTN, VER, BACKUP, RTC, SPU, HDD, FDD, ST224, ATAPI, ISO).
- **Attract mode:** WARNING → KONAMI → BEMANI → song list → title screen.
- **The practice stage:** the oracle's `bm3final-practice.his` runs unchanged: coins, mode select, sound select, then "Instant Love" with the DJ KONAMI tutorial, notes, BGA and judgements, with sound.

| Piece | Source |
|---|---|
| 68000 | Musashi (MIT, `third_party/musashi`, pinned commit in `COMMIT`), configured as a plain 68000 (`runtime/spu/hk_m68kconf.h`) |
| RF5C400 | `runtime/dev/rf5c400.*`, ported from MAME (BSD-3) |
| SPU board | `runtime/spu/spu.*`: MAME's memory map; dual-port RAM mailbox (PPC `0x3fe` → 68000 IRQ4, 68000 `0x3ff` → PPC EXT3); IRQ acknowledge register; wave RAM banks; the 500 Hz IRQ2/IRQ6 tick with ATA interrupts quantised to it; ATA DMA at 350 ns/word into wave RAM |
| SPU ATA | `runtime/dev/ata.*` gained ATA hard disks: IDENTIFY, PIO/MULTIPLE/DMA reads, LBA/CHS. Fed by the user's raw HDD image |
| Spectrum analyser | `runtime/firebeat/spectrum.*`, MAME's band model, fed from the SPU output |
| Audio out | `--wav FILE`; live playback in `--window` (SDL3 audio stream) |
| Input scripts | `--script FILE.his`: the oracle's input scripts, run by the runtime |

## Things the real hardware needed

- **BIOS time.** HIRAKU skips the BIOS. On the real machine the SPU powers up with it and tests all 32 MiB of wave RAM while the BIOS runs, about 21.6 s (MAME's first game-code access is at frame ~1299). Starting the game straight away made the SPU check time out (E704).
  - The runtime now lets that time pass with every device event running (`--bios-seconds`, default 21.65).
  - Frame numbers then line up with MAME's.
- **Power-on status.** An ATA hard disk powers up reporting DRDY|DSC (`0x50`); the SPU polls for it.
- **Supervisor-state system calls.** Interrupt handlers call kernel services through `sc` from supervisor state. The vector code handles that on the current stack, without a thread switch, and the glue now does too.

## Agreement with MAME (same input script)

- **Machine timeline:**
  - The SPU reports ready (`0x3f8 = 1`) at aligned MMIO record 23,708, as in MAME.
  - Our frame numbers are within about 30 frames of MAME's at the SPU check.
  - The next difference is a counter byte the SPU writes (`0x3a` vs `0x39`): timing, not logic.
- **Screens:** the same screen at the same frame number throughout (contact sheet in the M4 report). This is not pixel-identical:
  - Animations run at different phases, because of the ~30-frame timeline offset and different hit timing.
  - 1–52% of pixels differ per snapshot.
  - Proving the renderer exact needs equal GCU input: M3 (command-stream comparison, forced scenes).
- **Audio:**
  - Both 200 s long.
  - RMS per 10 s within about 5–15% of MAME's.
  - Envelope correlation 0.72 at **0 ms lag** over 120–150 s.
  - The remaining differences are keysounds triggered by slightly different judgements.
- **Spectrum analyser:** about 35,000 reads each, with the same value distribution.

## Speed

The 200 s practice run takes about 75 s of CPU, at about 2.7× real time. Most of that is still the interpreted exception glue (16.4M exceptions) and the 68000 (3.2G cycles). Recompiling the vector glue is the M9 performance work.
